### M3-R2 — child `error` ≠ выход (факт → файл/строка → тест/наблюдение → статус)

**RED / воспроизведение.** До правки `handleChildError()` по любому `error` безусловно ставил `entry.exited=true`, писал terminal `FAILED`/`OMP_SPAWN_FAILED` и удалял `tracked` entry. Живой TUI/RPC child с положительным PID, чей `kill()` синхронно отдаёт `error code:"EPERM"` и возвращает false без `close`, скрывался за `FAILED` (`closed:false`), терял ownership и переставал быть отменяемым. RED восстановлен: при отключённом раннем `return` тесты A–D/F падают `expected 'TERMINAL_OPEN'/'STARTING'/'RUNNING' to be 'CANCELLING'`; при возврате сырого `child.kill()` вместо `safeKill` тест E падает `Error: kill EPERM`.

**Правка (минимальное разделение).** `TrackedRun.spawnConfirmed` ставится в `track()` из `child.pid !== undefined` — единственное доказательство, что ОС создала процесс. `handleChildError()`: если `spawnConfirmed` — ранний `return` (ownership и слушатель `close` сохраняются; `exited`/waiters/tracking по одному `error` НЕ трогаются; публичной диагностики нет); иначе (истинный ENOENT: pid `undefined`, `close` не придёт) — прежнее terminal `FAILED`/`OMP_SPAWN_FAILED` (raw Error отброшен), чтобы spawn-failure не завис в `CANCELLING`. `safeKill()` оборачивает `child.kill()` в try/catch (проглатывает синхронный throw / недоставленный сигнал) на всех 3 площадках; сырой `child.kill()` остаётся только внутри `safeKill`.

**Состояние записи/child после 1-й и 2-й отмены** (тесты A/B/E, fake-child): после **первой** отмены — `state=CANCELLING` (non-terminal), `diagnostic=OMP_CANCEL_UNCONFIRMED`, `terminalQueued=false`, entry остаётся `tracked` и отменяемым, тот же живой child; после **второй** отмены — снова сигнал тому же tracked child, ни одной новой terminal-транзиции, `state` остаётся `CANCELLING`. Только собственный `close` child даёт ровно один terminal settle → `CANCELLED`. `reconcileAfterRestart` (тест F) переводит непокрытый `CANCELLING` в `INTERRUPTED`/`OMP_SUPERVISOR_OWNERSHIP_LOST` без сигнала по persisted PID.

### Дополнительно (найдено при повторе полного gate) — сериализация записей run-store

Не входит в исходные пункты 1–5, но раскрываю честно: при повторном прогоне полного gate обнаружен и устранён **реальный производственный дефект честного репортинга**, смежный с пунктами 1–2 (потеря подтверждённой отмены).

Fail-closed lock НЕ ослаблен: чужой процесс по-прежнему падает на `OMP_RUN_LOCKED`.

После локальной приёмки остаются отдельные крупные работы: поддержанный fixture-only native/context import через pinned OMP (с реальным созданием и повторным чтением новой OMP-сессии), затем перенос выбранных реальных transcript с проверенным backup; свежий платный Doctor VSLLM, публикация live v2, ограниченный реальный OMP-пилот; прочие профили, права/fallback, OMP-only cutover и разбор legacy. Подробные критерии и порядок — в [REMAINING_PLAN.md](../REMAINING_PLAN.md). **Каждая** операция с реальными секретами, пользовательскими homes, платным запросом, live v2 или production default требует отдельного точного решения пользователя; локальный успех результатов 1–4 не даёт такого разрешения.
