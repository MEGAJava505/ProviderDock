## M6.2 — локальная структурная диагностика VSLLM

1. Прочитай `src/diagnostics/provider-doctor.ts` и существующие tests. Зафиксируй перед кодом контракт минимальной структуры ответа, которая отличает native `incomplete/max_output_tokens`, completed без текста и иную proxy-форму. Разрешённый вывод: только allowlisted `status`, `incomplete_details.reason`, счётчики usage и типы `output`-элементов; строковые значения нормализуй к конечным безопасным кодам, счётчики — к конечным неотрицательным числам. Текст ответа, ключ, prompt, raw headers, request ID, произвольные provider strings и абсолютные пути в диагностическом выводе не нужны.
2. Если для следующего bounded запроса требуется код, сначала добавь fixture RED на недостающую классификацию/санитизацию, затем минимальную реализацию и GREEN. Сохрани fail-closed Doctor gate: пустой или неполный ответ не становится PASS, health snapshot не подменяется локальным fixture. Предпочти отдельный явно вызываемый diagnostic path, чтобы обычный Doctor не начал делать лишний потенциально платный запрос автоматически. Если существующего контракта достаточно, не добавляй код ради галочки — подготовь точную безопасную команду/план запроса.
3. Локально проверь как минимум native `status=incomplete`, completed с пустым `output`, proxy-ответ без `status` и payload с секретным canary: наружу выходят только структурные поля, canary отсутствует. Платный VSLLM-запрос в этом пакете **не выполняй** без отдельного решения пользователя; ранее сделанные два Doctor-запуска не означают разрешения на третий.

**Проверка:** fixture RED→GREEN для реально изменённого поведения; typecheck/targeted tests и, если менялся runtime, build + полный `npm test`. На Windows для полного suite используй process-local `TEMP`/`TMP` в `.provider-dock/test-temp` на E: (C: ранее давал `ENOSPC`), не меняя пользовательские переменные.

## M6.3 — gate и передача результата

1. Повтори локальную оценку VSLLM v2-кандидата против **последнего** Doctor snapshot и текущих доступных fingerprints. Ожидаемый при неизменном FAIL результат — `accepted:false`; не публикуй candidate. Подготовь для отдельного решения пользователя один bounded потенциально платный структурный запрос: точный профиль/модель, верхний предел output tokens, какие только поля будут сохранены и какой результат откроет повторный Doctor. Даже успешный структурный probe сам по себе не равен Doctor L3 PASS.
2. После отдельного будущего разрешения порядок остаётся: диагностика/свежий Doctor PASS → локальная пересборка и проверка v2 → отдельное разрешение на live v2 → новый preflight → отдельное разрешение на один реальный OMP-пилот. Если разрешения нет, остановись после локально проверяемого результата с честным blocker. Не начинай Chapter 3 import или Chapter 6 cutover в этом задании.
3. Пройди релевантный gate: целевые tests, typecheck/build/full suite по фактическому diff, `git diff --check`, отдельно проверь untracked-файлы и собственный diff на секреты/debug/skip.
