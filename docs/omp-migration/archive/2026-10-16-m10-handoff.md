## M10.3 — один настоящий сквозной browser fixture

Построй воспроизводимый сценарий с цепочкой:

`браузер → ProviderDashboardServer → OmpLaunchService → OmpRuntime / OmpProcessSupervisor → fake child / loopback → FileOmpRunRepository → dashboard`.

Переиспользуй существующие harness, route fixtures, fake child и browser helper. Допустим минимальный перенос общей fixture-сборки в test support или отдельный узкий integration smoke; сохраняй прежние сценарии. В этом доказательстве не подставляй готовый успех вместо OMP service/preflight/launch/run-store и не добавляй production bypass для synthetic route.

Через реальные элементы dashboard пройди проект с пробелами/кириллицей → provider/account → model → явное подтверждение прав → preview → preflight → launch → наблюдение результата. Run ID должен совпасть в HTTP, persistent record и UI; выбранный проект — с фактическим cwd child. Для успешного tool-read проверь результат, связанный с реальными байтами fixture-файла. Выбор API credential не должен подменяться portal session/OAuth; существующие неподдержанные варианты объясни пользователю без выдуманного успешного auth.

Подтверди минимум один отказ до spawn (нет подтверждения или изменилось evidence) и сброс устаревшего preflight после изменения выбора. Preview `ready` означает готовность к проверке/пилоту, но не пройденный пилот; браузер не должен выдавать fixture за production-ready. Сохрани meaningful RED для найденных UI/API дефектов, проверь GREEN, ошибки browser/network и скриншоты ключевых состояний.

**Критерий:** единый процессный сценарий воспроизводится командой; видимый результат подтверждён настоящим локальным launch stack. Если браузер недоступен, укажи конкретную причину и пометь этот пункт непроверенным; HTTP-only прогон не заменяет его.

## M10.4 — lifecycle, restart и пределы resume

Проверь запуск, отмену, потерю связи/ошибку child, restart и сохранность terminal records через имеющийся managed stack. Хотя бы cancel живого run пройди через browser/HTTP; состояние в UI должно соответствовать репозиторию. Повторный cancel terminal run не создаёт новый запуск. Неподтверждённая остановка остаётся `CANCELLING` до доказательства завершения, исходная причина аварии сохраняется.

В fixture перезапусти server/supervisor над тем же временным run-store и проверь ownership: старые orphan runs не оживают и чужие PID не сигналятся; terminal records сохраняются. TUI и RPC проверяй на тех поверхностях, которые реально поддерживаются: сейчас public selection задаёт TUI, direct harness умеет RPC. Не добавляй публичный RPC-режим ради теста.

Отдельно установи, есть ли поддержанный пользовательский resume. Если нет, зафиксируй это как открытый пункт реального lifecycle; `reconcileAfterRestart()`, повторный launch и импорт transcript нельзя называть native resume. Разработку новой resume-функции вынеси за этот пакет. Для Windows-пути различай проверку argv/cwd harness и shell-quoting установленного CLI.

**Критерий:** поддержанный локальный lifecycle проверен без ложного terminal/success; отсутствующий resume и actual-binary участок отмечены отдельно.

## M10.5 — ошибки, streaming и уже выполненный side effect

Переиспользуй failure matrix integration harness: 401, 403, 429, 5xx, обрыв streaming, exit до readiness и ошибка после выполненного tool-side-effect. По каждой строке проверь финальное/нетерминальное состояние, число запросов и применений side effect, отсутствие подмены маршрута/аккаунта/ключа. Причина отказа должна доходить до CLI/HTTP/UI безопасно, без marker credential, headers или сырых RPC-кадров.

Один отказ после запуска пройди через сквозной browser fixture из M10.3 и сопоставь UI с persistent record. Тест side effect должен проверять сам изменённый fixture-файл/счётчик, а не декларацию fake child. Ручное повторение операции не должно происходить автоматически при обновлении UI, повторном чтении runs или restart. Реальное поведение MCP остаётся `NOT PROVEN`, если доказательство использует только fake tool.

**Критерий:** каждой строке соответствует воспроизводимое доказательство; успешный соседний сценарий не маскирует отказ, автоматические retry/fallback не добавлены.

## M10.6 — финальный gate и документация

После каждого исправления запускай его целевые проверки. Для финальной версии выполни:

- целевые OMP runtime/service/supervisor/integration/HTTP/preview тесты из текущего `tests/`;
- `npm.cmd run typecheck`, `npm.cmd run build`, затем `npm.cmd test`;
- `node scripts/dashboard-ui-smoke.mjs` и `node scripts/dashboard-ui-smoke.mjs --negative`;
- команду сквозного сценария M10.3 с записанными exit/status и фактически просмотренными browser-состояниями;
- `git diff --check`, проверку ссылок изменённых документов и review собственного diff, включая новые untracked-файлы.

На Windows при риске ENOSPC задавай TEMP/TMP только дочерним процессам в своём temp-каталоге на E:. Убирай только созданные этим прогоном browser profiles/child/server после проверки ownership; глобальную уборку не выполняй. Если проверка упала, исследуй и исправляй причину в scope. Не превращай падение в PASS отключением assertions, skip, подменой реализации или расширением таймаута без доказательства причины.

Обнови главу 5 [плана](../REMAINING_PLAN.md) и [runbook](../../omp-runtime-runbook-ru.md): что подтверждено локально, что только по source, что требует реального пилота. Step 4 без свежего Doctor PASS/live v2/реального пилота; Step 5 по [решению M8](../STEP5_FIXTURE_IMPORT_DECISION.md) остаётся BLOCKED/NOT PROVEN. Никакого закрытия всей главы 5 или миграции только по fake-child gate.

**Критерий:** все доступные локальные пункты завершены и проверены; оставшиеся ограничения названы по пунктам, без смешения с локальным успехом.
