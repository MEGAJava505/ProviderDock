### Выбор мониторинга — решает пользователь и фиксирует в authorization

| Практический вариант Windows | Что даёт и где ограничения |
|---|---|
| **ETW process lifecycle + network/WFP events; Process Monitor для просмотра/экспорта процесса и I/O** | Предпочтительный базовый вариант при доступности источников: creation/exit/parent, PID и image path, network events. Сохранить event IDs, UTC conversion, session/config и dropped-event counts. Hash образов вычисляется отдельно и связывается с image event. Один Procmon или один WFP stream не гарантирует наблюдение всех попыток, отказов до сетевого стека, exit codes и application requests: нужны коррелированные controller/API observations. Проверить реальное покрытие до launch. |
| **AppContainer controller с журналированием + OS lifecycle/network monitor** | Controller может сохранить CreateProcess/Job/token данные, exit code, API error direct TCP и broker reject-before-network, request/byte counters. Требуются реальные события/перехват на нужном слое и независимое покрытие обходных прямых соединений actual процесса. Job/token attestation, захардкоженные нули и журнал только broker не доказывают полную сеть или дерево. Зафиксировать controller/config hash и источники каждого счётчика. |
| **PowerShell CIM/WMI polling (`Win32_Process`, при наличии event subscriptions) + сетевой монитор** | Подходит для baseline и post-teardown orphan check; записать polling interval и пропуски. Polling способен пропустить короткоживущих children и соединения; сам по себе не даёт полного lifecycle, надёжных exit codes, denied attempts или byte/request counters. Использовать как дополнение; без полноценного источника недостающих событий итог NOT PROVEN. |

Выбор не предписан; в `monitoringPlan` явно покрыть каждое требование. Если ни один доступный набор инструментов не покрывает их, **не расходовать actual launch**, оформить BLOCKED / A1 NOT PROVEN. Не менять audit policy, firewall или устанавливать инструменты глобально в рамках этого задания: недостающие возможности — ограничение, не повод расширить scope.

**Process tree.** Сохранить parent/controller PID → actual `omp.exe` PID → все обнаруженные child/descendant PIDs; для каждого узла PID+creation time (защита от reuse), parent PID, spawn/exit UTC, binary path и SHA-256, источник image/hash и exit code. Чувствительную часть пути публиковать как стабильный path alias/относительный путь, а точный путь и mapping держать в защищённом локальном источнике с hash-ссылкой; binary linkage должен оставаться проверяемым владельцем. Контролируемый launcher должен завершиться с наблюдаемым exit; долгоживущий host-shell обозначается отдельным ancestor вне run, без выдуманного exit. Attestation Job: activeProcessLimit=1, kill-on-close, actual membership, breakaway запрещён, cap enforcement/readback и источник. Controller/monitor/fixture вне Job перечисляются заранее отдельно; cap=1 относится к actual Job, а не ко всем инструментам Windows. Ожидается один `omp.exe` и отсутствие его descendants; каждый неожиданный child фиксируется и вызывает stop, а не исчезает из отчёта. После teardown — проверка Job и всех связанных PID/creation identities, orphan count и UTC; Job attestation не заменяет наблюдаемое дерево.

**Network.** С момента до spawn и до post-teardown монитор измеряет `attempted/allowed/denied`, connections, sent/received bytes и requests. У каждого счётчика — источник, единицы, baseline/final/delta, scope (actual PID/descendants, controller, fixture или probe), время и event refs; нули допустимы только при полном наблюдении. Попытки/решения и TCP packets/bytes — разные величины: определить правила подсчёта и дедупликации; attempted=allowed+denied только при общей единице/слое, иначе дать сверку с объяснением. Request counts берутся из наблюдаемого application/broker dispatch, не выводятся из TCP counts. Разрешённые обращения ограничены exact inert allowlist; внешний egress, DNS/UDP/IPv6 и обход broker также должны быть покрыты политикой и наблюдением. Нет данных — `null`/NOT PROVEN, не 0; billing не объявлять измеренным при отсутствии billing monitor.

В том же новом пакете нужны две **живые, заранее описанные отрицательные пробы**: direct TCP → отказ API с `EACCES` (либо фактический Windows `WSAEACCES`/10013 и явное отображение в EACCES), и unlisted route → reject-before-network. Для первой — probe PID, UTC, token/policy linkage, error code и monitor event; цель inert, без отправки во внешний интернет. Для второй — route alias, reject event до dispatch и наблюдаемая нулевая дельта сетевого dispatch по этому correlation ID. Пробы — inert helper/controller, отдельно от единственного actual launch, без второго запуска `omp.exe`, без создания descendants в actual Job; точный порядок и контекст изоляции указать заранее. Их счётчики отделены от actual telemetry: успешная probe не доказывает отсутствия попыток actual процесса. Блокировка на раннем API-слое может не породить WFP event — нужен наблюдаемый API-source, а не выдуманное событие. Ожидаемый отказ контрольной пробы не является unexpected egress; любая неожиданная попытка actual процесса за allowlist, даже denied, вызывает stop.

**Environment.** Сохранить fresh AppContainer/profile identity alias/hash, время создания, token/capability readback, Job binding, HOME/TEMP/cwd isolation, отсутствие наследованных credentials и provider configuration без dump значений окружения. Зафиксировать deny-by-default policy/config hash и allowlist ровно выбранного inert fixture (protocol/address class/port через разрешённый alias mapping); blanket network/loopback exception недопустим. Fresh attestation нужна для этого run, историческая `000045` её не заменяет.

### Stop и приёмка

**Немедленный stop:** unexpected child, unexpected egress/попытка actual вне allowlist, cap breach, timeout, hash/version mismatch, side effect вне owned fixture, потеря/неполнота monitor coverage или неизвестные counters. До launch это BLOCKED без запуска; после launch — остановить owned Job через watchdog/controller, сохранить события, провести teardown/orphan check. Не завершать посторонние процессы Windows. Записать execution **BLOCKED**, A1 **NOT PROVEN**, причину и фактические измерения; не повторять без нового явного разрешения. Истёкшее окно и неполный пакет также не разрешают второй launch. Negative probe с ожидаемым отказом не считается аварией; неожиданное разрешение этой пробы — stop.

**PASS возможен только одновременно:**

1. Ровно один pinned actual `omp.exe` 18.0.4 с совпавшим SHA-256; launch exit **0**, длительность **≤45s**, spawn/exit в утверждённом будущем окне, teardown в окне; без live/paid/credential/provider route.
2. Наблюдаемое дерево покрывает parent/controller, actual и всех children с UTC lifecycle, exit codes и binary path+SHA-256 linkage; Job cap=1 подтверждён, event loss/coverage gaps отсутствуют.
3. Attempted/allowed/denied и byte/request counters **измерены живым монитором actual run**, сверены с exact inert allowlist; **0 unexpected egress**, нет внешних отправленных bytes/requests. Direct TCP EACCES и unlisted reject-before-network наблюдаемы и отделены от actual counters.
4. После teardown **0 orphan** процессов; side effects ограничены owned fixture и заранее учтёнными monitor artifacts, fresh изоляция подтверждена.
5. Все новые integrity hashes совпадают, redaction чист в явно проверенном scope, все обязательные источники доступны. Неизвестное не заменяется нулём; config attestation не выдаётся за observation, inert preflight — за actual telemetry.
