## Результат 1. Один проверенный маршрут на один OMP-запуск

**Проблема в текущем коде.** `src/application/omp-launch-service.ts::launch()` вызывает `preflight(input)`, а затем повторно `selection(input)`. Между этими вызовами профиль, решение маршрута или credential generation могут измениться. Нельзя запускать маршрут B по успешной проверке маршрута A. Это не утверждение, что защита runtime уже обойдена; нужно закрыть именно разрыв на уровне service и доказать итоговое поведение.

**Сделай:**

1. В `tests/omp-launch-service.test.ts` создай детерминированный красный сценарий: источник решения/профиля меняет данные между первым и вторым чтением; `supervisor.start` не должен получить не проверенный preflight маршрут. Зафиксируй также случай, когда preflight падает: `start` не вызывается.
2. В `src/application/omp-launch-service.ts` сведи один `launch()` к одной выбранной immutable selection: её передают и в `runtime.preflight`, и в `supervisor.start` после успеха. Публичный `preflight()` остаётся отдельной проверкой для UI. Сохранить runtime recheck fingerprint перед созданием child environment и fail-closed при ротации/удалении ключа.
3. Добавь тесты на порядок операций, отсутствие второго выбора и безопасный diagnostic. Ни raw token, ни текст upstream-ошибки не должны попасть в ответ. Не добавляй автоматический retry/fallback при отказе.

**Область:** `src/application/omp-launch-service.ts`, его тесты; runtime/supervisor меняй только если регрессия докажет необходимость. **Приёмка:** красный тест воспроизводит разрыв на старой версии, на новой проходит; `runtime.preflight` и `supervisor.start` получают одну и ту же route identity, а изменение credential/profile между ними всё равно блокируется существующим runtime gate. Запусти `npx vitest run tests/omp-launch-service.test.ts tests/omp-runtime.test.ts tests/omp-process-supervisor.test.ts`.

## Результат 2. Объяснимый read-only маршрут в dashboard

**Проблема в текущем коде.** `buildOmpRouteReadinessPreview()` в `src/migration/omp-route-readiness-preview.ts` умеет объяснять `provider → account → model → protocol → origin → credential-state → evidence-state`, но используется лишь unit-тестами. В dashboard есть только preflight/launch: пользователь не видит, какое именно не-секретное решение или доказательство отсутствует.

**Сделай:**

1. Добавь в `OmpLaunchService` отдельный read-only метод preview, который собирает те же текущие несекретные profile/decision/evidence/Doctor/credential-revision **metadata** и вызывает существующий builder. Метод не требует pilot acknowledgement, не вызывает `runtime.preflight`, не читает значение ключа и не меняет файлы. Ошибки повреждённого/старого evidence должны превращаться в безопасный `blocked`/`unknown`, а не в PASS.
2. Подключи `POST /api/omp/preview` в `src/ui/provider-dashboard-server.ts` с Zod-валидацией явных `providerId`, `accountId`, `modelId`. Ответ — только allowlisted view model: verdict, reason, evidence tier и узлы цепи. Сохранить метод, лимит тела, session-token path и Host/Origin guard существующего сервера. Запрос не принимает путь проекта, credential value, произвольный URL или готовый decision от браузера.
3. В `provider-dashboard-script.ts`/`provider-dashboard-html.ts` покажи статус каждого узла рядом с формой OMP и следующий шаг понятным текстом. Обновляй preview при смене provider/account/model; не полагайся на ответ устаревшего асинхронного запроса после нового выбора. Preview — **объяснение**, не разрешение запуска: кнопка запуска остаётся закрытой до отдельного успешного preflight и acknowledgement; смена выбора сбрасывает preflight.
4. Проверь минимум пять случаев: нет decision; битый v1/v2 evidence; устаревший Doctor или generation ключа; совпадающий локальный smoke без real-pilot; корректное решение. Даже в последнем случае UI говорит «можно проверить preflight/провести пилот», не «OMP уже проверен в реальном провайдере» и не «готово к production». HTTP/DOM тест должен показать, что ответ и HTML не содержат fake-secret, raw headers, cookie или абсолютный source path.

**Область:** `src/application/omp-launch-service.ts`, `src/migration/omp-route-readiness-preview.ts` только при доказанном дефекте, dashboard server/script/html/css и существующие `tests/omp-route-readiness-preview.test.ts`, `tests/provider-dashboard-omp.test.ts`, dashboard smoke. **Приёмка:** пользователь видит точный блокер до preflight; preview не авторизует launch и не инициирует сеть; негативные HTTP/DOM сценарии зелёные; реальный локальный dashboard smoke проходит.

## Результат 3. Несколько API-ключей и безопасная смена активного — прямо в dashboard

**Проблема в текущем коде.** `CredentialManager` и CLI уже поддерживают несколько ключей на провайдера, маску, активацию и защищённое удаление. Dashboard показывает masked-список, но рядом написано «управление: providerdock credentials»: добавить второй ключ и переключить активный из UI нельзя. Это пользовательский сценарий, о котором просили раньше.

**Сделай:**

1. Используй существующие `ProviderDockApplication.addCredential`, `activateCredential`, `removeCredential`, `listCredentials`; новый формат хранения/шифрования не придумывай. Добавь узкие JSON-эндпоинты для `add`, `activate`, `remove` под `/api/credentials` с жёсткими schema/purpose/provider/id проверками. Значение нового ключа допустимо **только** в теле add-запроса и немедленно передаётся менеджеру; в snapshot, ответ, diagnostic, лог и URL попадают лишь id/маска/state. Режим `portal-session` не смешивается с `provider-api`.
2. В списке ключей dashboard добавь форму «добавить» (label, purpose, secret, необязательная явная активация), действие «сделать активным» и «удалить» только для неактивного и неиспользуемого ключа. Поле secret — password, очищается после успеха **и** ошибки; старый ключ не удаляется при добавлении/смене. Пользователь может держать несколько ключей и выбрать один активный для назначения.
3. Если vault/registry недоступен или повреждён, покажи `unavailable`/`recovery-required`, не «ключей нет». Не обходи `CredentialManagerError` и не подключай обычный `/api/secrets/:ref` к управляемым ключам. Backup/restore остаются CLI-only: не передавай пароль backup или путь файла через браузер.
4. Добавь регрессии для двух ключей одного провайдера, независимых `provider-api` и `portal-session`, явной активации, запрещённого удаления активного/используемого, ротации с сохранением старого, недоступного vault и утечки секретов в HTTP/HTML/log. После смены активного provider-api диагностическое Doctor evidence должно инвалидироваться через существующий application method; OMP preview/preflight не должен продолжать принимать прежний credential fingerprint.

**Область:** dashboard server/script/html/css, при необходимости узкие application-test фиксы; `src/core/security/credential-manager.ts` и формат registry не менять без воспроизведённого дефекта. Тесты добавляй в существующие dashboard/credential suites. **Приёмка:** в изолированном dashboard на fixture можно добавить два ключа, активировать второй, увидеть только маски, сохранить первый для отката; попытка удалить активный отвергается; после переключения старое OMP evidence не проходит gate. Пройди HTTP-тест и dashboard smoke без живого профиля.
