## ЭТАП 0. ЗАФИКСИРУЙ ФАКТИЧЕСКУЮ БАЗУ

1. Запусти git status --short, git branch --show-current, git log -1 --oneline. Сравни с исходной точкой выше; запиши отличия до правок.
2. Убедись, что оба файла этой папки реально переданы тебе. Сейчас они могут быть untracked и не попадут в обычный Git clone без явного включения в передачу. Если отсутствуют, запроси их; не реконструируй задание по старым датированным handoff.
3. Перечисли доступность только нужных доказательств: .scratch/omp pinned checkout, .provider-dock/tools/omp-0c6c981ee583/omp.exe, названных в Step 4 provenance assessment JSON и внешнего smoke-report на F:. Их отсутствие не обходить новым источником или guessed hash.
4. Прогони npm test, npm run typecheck, npm run build, node scripts/dashboard-ui-smoke.mjs, node scripts/omp-import-probe.mjs, git diff --check. Сохрани exit code, число файлов/тестов и точный probe verdict. git diff --check не покрывает untracked-файлы.

**Этап принят, когда:** есть воспроизводимый baseline и перечень missing/stale артефактов. При красной проверке сначала изучи сообщение и локализуй причину; не переходи к утверждению «прошло».

## ЭТАП 1. ПРОВЕРЬ КОНСОЛИДАЦИЮ ТЕСТОВ И ГРЯЗНЫЙ DIFF

1. Просмотри git diff --cached и git diff; отдельно включи untracked-файлы. Сопоставь каждый удалённый test suite с оставшимся родственным файлом: сохранены ли негативные сценарии, assertions, названия групп и реальное поведение. Считай файлы и физические строки tests/*.test.ts вместе с tests/support.
2. Проверь новые OMP/credential/portal/session модули на непреднамеренное расширение scope, секреты, debug, временные обходы, skip/only и незащищённые live routes. Не меняй чужие файлы лишь ради чистого статуса.
3. Если обнаружен конкретный дефект, сформулируй наблюдаемый критерий, сделай минимальную красную fixture-регрессию, исправь причину и проверь зелёный результат плюс затронутые соседние тесты. Если дефекта нет — не рефакторь ради уменьшения числа файлов.

**Этап принят, когда:** дана проверяемая матрица «удалённый suite → куда перенесены сценарии → что проверено» и список реальных замечаний; один зелёный общий счёт тестов не выдаётся за эту матрицу.

## ЭТАП 2. ПРОВЕРЬ STEP 4 БЕЗ СЕТИ И LIVE-ПУБЛИКАЦИИ

1. На имеющихся несекретных артефактах перепроверь pinned source commit, executable hash, inventory/smoke SHA, точные provider/account/origin/baseUrl/protocol/model/capabilities и v2-схему. Раздели «пересчитано сейчас», «только старый Doctor snapshot», «можно проверить лишь при живом preflight».
2. Убедись, что локальный loopback report не назван реальным upstream PASS, а локальное launchAuthorized:false не выдано за опубликованное live v2. Не считывай значения credentials ради этой проверки.
3. Для остальных профилей подготовь список недостающих не-секретных решений и unsupported transport constraints; не создавай принятых решений за пользователя.

**Этап принят, когда:** для каждого утверждения указан источник/срок годности и точный блокер. При отсутствии ignored или F:-артефакта зависимая часть получает статус «доказательство недоступно».

## ЭТАП 3. ПРОВЕРЬ STEP 5 ТОЛЬКО НА FIXTURES

1. Запусти статический OMP import probe и соответствующие тесты инвентаря, плана, manifest и preview. Проверь fail-closed статус для symlink/hardlink/изменившегося объекта и отсутствие обещания полной Windows TOCTOU-защиты.
2. Убедись, что staged не назван imported без созданной и повторно прочитанной OMP-сессии; повторная запись manifest не теряет прежнюю историю и не меняет target scope.
3. Сформулируй короткий технический выбор между поддержанным Bun-харнессом с explicit synthetic root и публичным OMP API. Пока нет отдельного решения, не запускай новый importer и не пиши вручную OMP SQLite/JSONL. Если найден новый безопасный интерфейс, докажи его на синтетике после согласования нового шага.

**Этап принят, когда:** fixture-поведение доказано, а native importer честно остаётся unsupported либо имеет новое независимое доказательство; реальные сессии не читались.

## ЭТАП 4. ВЕРНИ ПРИЁМКУ И ОСТАНОВИСЬ НА ВНЕШНИХ РЕШЕНИЯХ

После локальных этапов верни один отчёт:

- baseline и обнаруженный дрейф;
- таблица «этап → проверка/артефакт → PASS, FAIL или BLOCKED»;
- точные изменённые тобой файлы и red → green для каждого исправления;
- судьба объединённых тестов и число тестов/файлов/строк без подмены смысла;
- что известно о VSLLM v2 и других 17 профилях, что зависит от старого Doctor, что отсутствует;
- точная граница fixture-import и текущие риски сканера;
- требуемые решения пользователя **раздельно**: платный Doctor, публикация live v2, один платный OMP-пилот, путь native importer, доступ к реальным source roots, cutover.

Не открывай новый Markdown-файл задания. Обнови эти два файла только для подтверждённого изменения статуса. Если одно внешнее решение ещё не получено, продолжай независимую разрешённую локальную работу; зависимую часть пометь BLOCKED и останови.

## УСЛОВНЫЕ ПОСЛЕДУЮЩИЕ ЭТАПЫ — ТОЛЬКО ПОСЛЕ РЕШЕНИЙ

1. **VSLLM:** после каждого соответствующего разрешения — свежий Doctor выбранной модели, проверенный v2 decision/evidence, отдельная live-публикация, preflight и один реальный OMP-пилот. Gate accepted-for-pilot означает лишь готовность провести пилот; успех пилота и production-готовность доказываются отдельно.
2. **История:** после согласования поддержанного importer и успешного fixture-import — утверждённые source roots, остановка writers, проверенный backup, отдельное согласие на живые transcript и пофайловая приёмка. Оригиналы сохранить.
3. **UI/routing:** после реальных пилотов — права, TUI/RPC lifecycle, fallback fault matrix и защита от повторного side effect. Без этого automatic fallback остаётся выключенным.
4. **Cutover:** после решения по каждому актуальному профилю и OMP-only acceptance — карта keep / migrate / delete, отдельное удаление legacy-кода и финальный rollback check. Пользовательские homes и установки старых CLI не удалять автоматически.

**Финальная граница:** никакая локальная зелёная матрица не расширяет полномочия на живые данные, платный запрос или удаление старого контура.
