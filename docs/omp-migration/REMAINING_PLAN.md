# ПОДРОБНЫЙ ПЛАН ОСТАВШЕЙСЯ РАБОТЫ

Срез: 25 сентября 2026 года. Это карта незавершённой миграции ProviderDock на OMP. Пошаговый документ для исполнителя — [AGENT_HANDOFF.md](AGENT_HANDOFF.md). Текущий код и свежие проверки важнее датированных отчётов; исторический [исходный план](../superpowers/plans/2026-09-14-omp-migration-ru.md) не является очередью заданий.

## ГЛАВА 1. ПРИНЯТЬ И СОХРАНИТЬ ТЕКУЩУЮ БАЗУ

1. Снять git status, текущий commit и перечень untracked; сохранить границу авторства. Два файла в этой папке сейчас тоже могут быть untracked: при передаче через Git их нужно явно включить в передаваемую версию. Не считать наличие файла в локальной директории доказательством, что его получит следующий исполнитель.
2. Просмотреть staged и unstaged diff отдельно. Для каждого удалённого тестового файла сопоставить старые сценарии с новым родственным suite; одинаковый общий счёт 1041 не доказывает сохранение каждого негативного assertion. Считать размер тестов вместе с tests/support, не переносить строки ради уменьшения числа файлов.
3. Прогнать npm test, npm run typecheck, npm run build, node scripts/dashboard-ui-smoke.mjs, node scripts/omp-import-probe.mjs и git diff --check. Новые untracked-файлы проверить отдельно: diff --check их не охватывает.
4. Для выявленного дефекта — воспроизводимая красная проверка, минимальная правка, зелёная проверка. Никаких случайных сбросов чужих изменений или коммитов за другого автора.

**Приёмка:** описан точный текущий baseline, все удалённые тестовые сценарии учтены, целевые и полные проверки имеют свежие результаты. Если интеграция не зелёная, следующие главы не объявлять принятыми.

## ГЛАВА 2. STEP 4 — ПРИНЯТЬ МАРШРУТЫ ПРОВАЙДЕРОВ

Различать три состояния:

1. **Готов к пилоту:** текущий профиль, account, credential generation, Doctor L3, v2 decision, provenance закреплённого бинарника и локальный smoke совпали; preflight разрешает ограниченный первый OMP-запуск. Это смысл статуса accepted-for-pilot в коде, а не доказательство, что OMP уже обращался к реальному провайдеру.
2. **Пилот прошёл:** ограниченный OMP-запрос действительно выполнен, результат/stream/tool-поведение и стоимость проверены, диагностические данные не раскрывают ключ. Прямой Doctor или loopback не заменяют этот пункт.
3. **Готов к повседневной работе:** дополнительно приняты права, инструменты, ошибки, resume, fallback и пользовательский путь. Только это состояние может вести к cutover.

### VSLLM

Локальный v2-кандидат и его хеш-цепочка описаны в [Step 4 provenance](../omp-step4-provenance-2026-09-24.md). Doctor PASS в decision опирается на сохранённый снимок от 23 сентября; его wall-clock свежесть gate сам по себе не проверяет. Assessment-файлы лежали в игнорируемой Git зоне .provider-dock/omp-mapping-2026-09-16-ExxykD/, а smoke-report — на F:/ProviderDockBuild/. Эти пути являются локальными доказательствами, не частью Git: отсутствие файла на другой машине означает «доказательство недоступно», а не PASS. Значение sourceCommit 0c6c981ee5838d97700180383077eb0a3790637c относится к upstream OMP, не к commit ProviderDock.

Порядок: сверить не-секретные providerId/accountId/origin/baseUrl/protocol/model/capabilities и точный профиль → с отдельного разрешения выполнить свежий потенциально платный Doctor L3 → собрать и локально проверить v2 evidence/decision → с отдельного разрешения опубликовать их в живом профиле → повторить preflight → с отдельного разрешения провести один ограниченный реальный OMP-пилот. Между шагами повторно сверять configuration/credential fingerprints; изменение ключа или профиля делает прежнее доказательство недействительным.

### Остальные профили

Для каждого из оставшихся 17 профилей нужны явные accountId, утверждённый origin/baseUrl, protocol, model и наблюдённые capabilities. Статический header или сторонний Messages x-api-key нельзя молча объявить поддержанным транспортом; unresolved auto нельзя угадать. Вести пофайловую/профильную матрицу: pending, migrated-and-tested либо явно принятый пользователем unsupported с причиной. Если фактический inventory изменился, сначала пересчитать полный набор.

**Приёмка:** каждый профиль имеет проверяемое решение или честный блокер; ни один не принят по результату другого. Публикация live v2, платный Doctor и реальный OMP-запрос — три самостоятельных границы разрешения.

## ГЛАВА 3. STEP 5 — ПЕРЕНЕСТИ ИСТОРИЮ БЕЗ ПОТЕРЬ

[Блокер закреплённого importer](../omp-step5-import-blocker-2026-09-24.md) воспроизводится статическим probe: CLI-picker берёт стандартный source home, Codex store требует bun:sqlite, exit 0 при пустом picker не означает импорт. Инвентарь и manifest на fixtures не являются доказательством переноса. На Windows текущий переносимый Node-сканер не является полноценной защитой от конкурентной подмены в живом/недоверенном root.

1. Согласовать технический путь: поддержанный Bun-харнесс с explicit synthetic source root, изолированным target и сетевой изоляцией либо публичный OMP API. Исследование пути разрешено локально; запуск нового upstream-кода/Bun, изменение его контракта или работа с живыми homes — отдельная точка решения. Не писать напрямую OMP SQLite/JSONL.
2. На синтетических Codex/Claude transcript доказать создание новой OMP identity, порядок сообщений, tool-call/result linkage, cwd, model metadata, provenance, безопасное прерывание и идемпотентность повтора. Статус imported присваивать только после повторного чтения фактической целевой сессии.
3. До живого импорта выбрать точные source roots и target, остановить writers, создать и проверить quiescent backup, зафиксировать права на чтение. Пока race-граница не доказана, работать только с контролируемой копией, а не с недоверенным live root.
4. После отдельного согласия на реальные данные дать отчёт по каждому источнику: imported, already imported, unsupported, corrupt или skipped by user. Оригиналы оставить read-only. Transcript переносит контекст, но не прежние permissions, OAuth, hooks, MCP, extensions, sandbox и не native resume старого клиента.

**Приёмка:** fixture-import с новой проверенной OMP-сессией и повтором без дубликата предшествует любому доступу к реальным transcript; затем каждый исходный файл учтён без раскрытия содержимого.

## ГЛАВА 4. СОХРАНИТЬ CREDENTIALS И КАБИНЕТЫ

Не перестраивать уже работающий credential manager: он разделяет provider-api и portal-session, хранит несколько ключей с одним активным для назначения, маскирует значения и не переключает платный запрос на другой ключ автоматически. Исторический handoff сообщал, что ключ из .env-key импортирован под новой защищённой ссылкой, а старый ciphertext сохранён; это не свежая проверка.

Историческая приёмка VSLLM portal account 16568 сообщала о сохранении исходного повреждённого accounts.json: 280047 NUL-байт, SHA-256 88894e28ee6b8da1255d95b5cd2ada7e2729eae5d6fa90a6a3179f4d0f686e43, копия в .provider-dock/omp-mapping-2026-09-16-ExxykD/portal-recovery-backup-vsllm-2026-09-23/portals/accounts.json. Наличие и hash копии требуется проверить перед rollback; путь локальный и может отсутствовать в другой копии.

Осталось: проверить список зашифрованных записей и активных привязок только через masked-интерфейс; проверить portable backup/restore на изолированной копии; установить связь provider/account/session для остальных кабинетов; показывать unavailable/recovery-required вместо «аккаунтов нет». При ротации новый ciphertext и новая привязка должны быть подтверждены до удаления старого.

**Приёмка:** у каждого кабинета виден проверенный статус, backup восстанавливается без замены живого файла, старые ключи и cookie остаются доступными для безопасного отката.

## ГЛАВА 5. STEP 6 — ПРИНЯТЬ ПОЛЬЗОВАТЕЛЬСКИЙ OMP-КОНТУР

Read-only route-preview уже есть, но production routing и fallback не приняты. UI должен различать «можно провести пилот» и «принято для повседневной работы». До реального пилота допустим статус первого типа, если gate принят; второго — нет.

1. Проверить последовательность проект → провайдер/аккаунт → модель → права → preflight → OMP; отдельно показать API key, portal session и OAuth и конкретный отсутствующий узел evidence.
2. Пройти интегрированный TUI/RPC lifecycle: запуск, отмену, restart/resume, потерю связи, неуспешный ответ, Windows-путь с пробелами/кириллицей. Локальные отдельные smokes не заменяют этот сценарий.
3. Проверить 401/403/429/5xx, streaming и момент, когда tool/MCP уже сделал побочный эффект. Автоматический fallback допустим только при доказанном отсутствии повторного side effect; иначе оставить явный retry.
4. Принять отдельную модель прав для shell/write/network/MCP/extensions и project bindings. Старые full-auto flags не импортировать как новые разрешения.

**Приёмка:** UI правильно объясняет blocked/unknown/stale/ready-for-pilot и не обещает production-готовность до всех проверок безопасности и пользовательского сценария.

## ГЛАВА 6. STEP 7 — CUTOVER И УДАЛЕНИЕ LEGACY

После успешных реальных пилотов в нескольких проектах и результата для каждого актуального профиля провести OMP-only acceptance: старые codex/claude недоступны в PATH, старые bridges выключены, старые homes не используются, а запуск, работа, cancel и resume остаются рабочими. Подготовить проверенный rollback snapshot до изменения production default.

Только после этой приёмки сделать OMP единственным production launch. Затем составить поимённую карту keep / migrate / delete для legacy CLI, launchers, runtime generation, bridges, config, tests и docs; удалить старый код отдельным reviewable изменением. Полезные protocol/replay сценарии перенести в OMP-контрактные тесты. Архивы сессий и пользовательские homes сохранить. Удаление установленных старых CLI — отдельное решение пользователя.

**Приёмка:** OMP-only работает без старых executables, homes и bridge-зависимостей; восстановление старой версии возможно по проверенному snapshot. Зелёные unit-тесты сами по себе не разрешают cutover.

## ГЛАВА 7. ЗАКРЫТИЕ И ДОКУМЕНТАЦИЯ

После каждой принятой границы обновлять этот план и [runbook](../omp-runtime-runbook-ru.md), помечать дату и фактическое доказательство, а не создавать новые agent-next-task файлы. [PROJECT-MAP](../PROJECT-MAP.md) остаётся картой архитектуры. На финале — полный тестовый gate, реальный пользовательский сценарий, diff review, проверка отсутствия секретов/debug/skip и понятный отчёт о неподдержанных профилях и сессиях.

**Приёмка:** текущая инструкция, исторические доказательства и ещё требующие пользовательского решения действия различимы без устного пояснения.
