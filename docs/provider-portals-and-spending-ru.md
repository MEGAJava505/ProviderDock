# Кабинеты провайдеров, кошельки, check-in и тарифы

7 сентября 2026. ТЗ по уточнённому запросу: провайдеров стало в несколько раз больше;
нужен единый обзор с автоматическим чтением их витрин и личных кабинетов. Приоритет:
**кошелёк → доступность ежедневного check-in → личные тарифы → контроль расходов**.

Статус: общая витрина, ручная оценка расходов и первое подключение кабинетов New API
реализованы. Кошелёк и check-in читаются с отдельным токеном кабинета; есть автообновление,
раздельные ошибки и защита от устаревших результатов после смены подключения. Порядок
подключения и ограничения — в [инструкции](provider-portal-setup-ru.md).
Загрузка стандартных тарифов New API по группам и опубликованной статистики теперь
реализована: [витрина моделей](model-storefront-ru.md). Другие платформы, динамические
формулы, согласованные тарифы и блокировка расходов ещё не реализованы.
Без авторизованного источника личный кошелёк и check-in отображаются как неизвестные.

## Что увидит пользователь

В карточке каждого провайдера:

- доступный баланс, валюта/кредиты, отдельно бонусы и подписка, если сайт их различает;
- когда баланс получен, из какого аккаунта и по какой ссылке открыть кошелёк;
- check-in: «можно забрать», «уже получен», «отключён», «нужен вход» или «нет данных»;
- следующая дата check-in с часовым поясом сайта, если сервер её сообщает;
- состояние подключения кабинета и последнее успешное обновление.

В общей витрине:

- модель, провайдер, протокол, результаты проверки текста/потока/инструментов;
- тарифы входа, выхода, чтения/записи кэша и платных инструментов;
- единицы оплаты: миллион токенов, запрос, изображение и т. п.;
- группа аккаунта, множитель, валюта, источник и время получения цены;
- предыдущий тариф и изменение, отметка превышения настроенного порога;
- отдельные метрики витрины: TPS, средняя задержка и доля успешных запросов; для каждой
  источник, единица, время обновления, период и размер выборки, если сайт их сообщает;
- нагрузка только при наличии отдельной метрики сайта; отдельно локальные задержки,
  ошибки и 429 с размером выборки и периодом наблюдений.

Поиск работает сразу по всем провайдерам. Модели с одинаковыми названиями не сливаются:
разные endpoints могут давать разные версии и возможности. Сопоставление для сравнения
можно задавать отдельно; оно не меняет ID маршрута. По умолчанию список постраничный,
без автоматической платной проверки сотен моделей.

## Подключение

1. Пользователь добавляет API Base URL и ключ для генерации. Discovery загружает модели.
2. В карточке выбирает «Подключить кабинет» и задаёт адрес сайта/профиля/витрины. Сайт
   может отличаться от API-хоста; связь задаётся явно для выбранного профиля.
3. ProviderDock определяет поддерживаемую платформу и показывает доступные способы
   авторизации. Для сайтов с официальным account token используется отдельный токен;
   если сайт принимает только веб-сессию, нужен отдельный поддерживаемый вход.
4. Проверяется чтение аккаунта; пользователь видит нормализованный результат:
   идентификатор аккаунта, баланс, статус check-in, группу тарифов, дату обновления.
5. Для других сайтов подключается адаптер платформы или адаптер конкретного варианта.
   Неизвестная платформа остаётся с рабочим API-профилем и неподключённым кабинетом.

Генерационный API-ключ нельзя считать ключом к кабинету. Токены кабинета не передаются
CLI и хранятся через SecretStore отдельно от генерационных ключей. Пароли/cookies не
нужно отправлять в чат. В интерфейс возвращаются состояние подключения и нормализованные
поля, но не cookies, токены или полные ответы личного кабинета. При истечении входа
обновление приостанавливается; последнее значение отмечается устаревшим.

Автоматизация авторизованного браузера возможна как дополнительный вариант после
отдельной поддержки сайта; она не является универсальным способом извлечения. HTML без
выполнения JS часто не содержит ни баланса, ни тарифов. Предпочтителен тот JSON endpoint,
который использует собственный интерфейс сайта и который разрешён данному аккаунту.

## Одно ядро, подключаемые адаптеры

Bridge отвечает за сообщения, инструменты и завершение генерации. Работа с кабинетом —
отдельный `ProviderPortalAdapter`. Один адаптер платформы обслуживает много провайдеров;
различия форков оформляются явными возможностями/версиями и проверенными нормализаторами.
Имена доменов сами по себе не подтверждают поддержку API платформы.

### Основной сценарий: много сайтов одного семейства

По уточнению пользователя большинство его провайдеров используют почти одинаковые
витрины и кабинеты; различия обычно небольшие, полностью другие сайты — исключение.
Это рабочая гипотеза для порядка реализации, а не доказательство одинаковых API.

Реализацию разделить на три уровня:

| Уровень | Что содержит | Когда нужен |
| --- | --- | --- |
| Адаптер семейства | Авторизация, чтение кошелька/check-in/тарифов, проверка схем и единиц | Большинство сайтов с подтверждённым общим API |
| Вариант семейства | Проверенные отличия endpoint, полей JSON, способа входа или расчёта тарифа | Форк с небольшими изменениями |
| Отдельный адаптер | Другой контракт кабинета с тем же нормализованным результатом | Сайт с принципиально другим API |

URL сайта, ссылки на секреты, аккаунт и выбранный вариант хранятся в подключении
провайдера. Исправление общего адаптера применяется ко всем его подключениям. Вариант
не должен копировать весь адаптер: он меняет только явно перечисленные операции.
Разница в оформлении страницы не требует варианта, если контракт API прежний.

При добавлении сайта обнаружение проверяет известные metadata-ответы и возможности
без генерации. Идентификация платформы предварительная до проверки схемы ответа.
Кошелёк, check-in, тарифы и статистика проверяются независимо: изменение одной операции
не отключает рабочие операции и сам API генерации. Ошибка чтения тарифов сохраняет
последний снимок как устаревший и учитывается строгим режимом контроля расходов.

Расширение на провайдеров не должно требовать ручного сбора данных каждого сайта:
сначала собрать обезличенные схемы одного типичного кабинета, реализовать семейство,
затем проверить повторное использование на втором сайте. Дополнительные данные
запрашивать для неподдерживаемого варианта с указанием конкретной операции/ошибки.
Сопоставление по внешнему виду не включает адаптер без проверки ответа API.

Приёмка переиспользования: два домена с одинаковыми фикстурами используют один адаптер;
вариант с другим check-in endpoint меняет только check-in; отсутствующий check-in
оставляет кошелёк и тарифы рабочими; неизвестная схема кошелька не становится нулевым
балансом; секреты и кэш аккаунтов разных доменов остаются раздельными.

Предлагаемый интерфейс:

```ts
interface ProviderPortalAdapter {
  detect(site: URL): Promise<PortalCapabilities>;
  readAccount(connection: PortalConnection): Promise<AccountSnapshot>;
  readCheckIn(connection: PortalConnection): Promise<CheckInSnapshot>;
  readPricing(connection: PortalConnection): Promise<PricingSnapshot>;
  readPerformance?(connection: PortalConnection): Promise<PerformanceSnapshot>;
  readLoad?(connection: PortalConnection): Promise<LoadSnapshot>;
}
```

Существующий реестр provider plugins можно расширить отдельной возможностью кабинета.
Первым добавить семейство New API, но с проверкой версии/форка. Остальные семейства
подключать по примерам реальных сайтов. Это не требует нового bridge для каждого домена.

Каждое значение содержит `sourceUrl`, `observedAt`, `expiresAt`, `accountFingerprint`,
`status` (`known`, `unknown`, `auth-required`, `unsupported`, `error`) и нормализованный
payload. Старое успешное значение хранится отдельно от результата последнего обновления.
Разные аккаунты одного сайта не делят кэш. Изменение аккаунта, группы, адреса кабинета
или API-профиля инвалидирует соответствующие снимки и согласованные тарифы.

Для кошелька хранить единицы сайта и нормализованную сумму только при проверенной
формуле. `quota`, кредиты, бонусы и USD нельзя смешивать. Показанное в кошельке число
не вычислять вычитанием локального usage: вне ProviderDock тоже могут идти запросы.

Для check-in отдельно хранить:

```text
featureEnabled: true | false | unknown
accountEligibility: available | claimed | disabled | auth-required | unknown
siteDate / siteTimeZone / nextEligibleAt: значение сайта либо unknown
reward: известный размер/диапазон либо unknown
```

Глобальный флаг «функция включена» не означает, что награда доступна сегодня этому
аккаунту. Проверка статуса использует только чтение. Получение награды — отдельная
пользовательская команда; автоматический POST для check-in в это ТЗ не входит.

## Что подтверждено на SeekAI

Проверены публичные страницы [витрины](https://seekai.cc/pricing) и
[профиля](https://seekai.cc/profile) без учётных данных. Обе возвращают SPA с заголовком
`New API`. Общий публичный JS использует `/api/user/self`, `/api/user/self/groups`,
`/api/pricing`, `/api/status`, а также обновление авторизации `/api/user/auth/refresh`.
В коде есть структуры `access_token`, `token_type`, `access_expires_at` и настройки
check-in. Значения токенов или личные данные не читались.

Проверка [публичного статуса](https://seekai.cc/api/status) вернула HTTP 200 и
`checkin_enabled: true`, `quota_per_unit: 500000`, `quota_display_type: "USD"`.
Запрос [тарифов](https://seekai.cc/api/pricing) без входа вернул HTTP 401 с JSON-ошибкой.
Это наблюдение на момент проверки, а не постоянная характеристика сайта.

После этого пользователь прислал обезличенный список запросов своего браузера:
`/api/user/self`, `/api/user/checkin`, `/api/status`, `/api/pricing`,
`/api/perf-metrics/summary`. Эти пути совпали с текущими маршрутами upstream New API.
По исходникам реализован общий адаптер кошелька/check-in; реальный публичный статус
SeekAI успешно прочитан этим адаптером. Авторизованные ответы аккаунта пользователя
пока не получены: правильность его персонального баланса, статуса и тарифа не заявляется.
Автоматическое получение/обновление веб-сессии и cookies не реализовано.

### Уточнение по скриншотам пользователя

Скриншоты предоставлены пользователем 7 сентября 2026. Это наблюдение интерфейса,
а не авторизованная проверка API; персональные идентификаторы и суммы в ТЗ не копируются.

- Витрина поддерживает карточки/таблицу, поиск, переключение единиц `/1M` и `/1K`,
  режимы «Стандартный» / «Пополнение». Значение этих режимов нужно подтвердить в данных;
  не считать второй режим автоматически скидкой или ценой генерации.
- В подробностях модели есть базовая цена входа/выхода/кэшированного входа и отдельная
  таблица групп с коэффициентом и итоговыми ценами. Хранить исходный тариф и итоговый
  тариф раздельно; не применять коэффициент второй раз к уже рассчитанной цене.
- TPS обозначен в токенах/секунду, задержка — в секундах, успешность — в процентах.
  Не путать среднюю задержку с временем до первого токена без подтверждения методики.
  Красный индикатор «Стат.» не трактовать как процент загрузки оборудования.
  Если период и размер выборки не указаны, оставить их неизвестными.
- Теги `Reasoning`, `Tools`, контекст и «конечные точки: openai» — заявленные сайтом
  возможности. Само слово `openai` не различает Responses и Chat Completions и не заменяет
  проверку истории инструментов. Заявленные и проверенные возможности хранить отдельно.
- В профиле видны текущий остаток квоты, общее использование и группа аккаунта. Символ
  `$` в UI сам по себе не подтверждает соответствие бонусных единиц реальному доллару.
- Check-in показывает состояние сегодняшнего входа, награду за сегодня, число отметок,
  сумму за месяц, общую сумму и календарь. Подпись «Зарегистрирован» выглядит как отметка
  уже выполненного check-in; точное соответствие `claimed` нужно подтвердить JSON-полем.

### Первое получение схемы запросов из кабинета

Подготовлен [пассивный сборщик адресов](../scripts/collect-portal-endpoints.browser.js).
На уже открытой странице профиля нужно раскрыть блок ежедневного входа, затем выполнить
его в DevTools Console. На странице витрины открыть подробности модели/производительность
и повторить. Прислать два текстовых результата с пометками «профиль» и «витрина».

Скрипт читает только браузерный список уже произошедших fetch/XHR-запросов текущего сайта.
Он не отправляет запросы и не получает награду, не читает cookies, хранилища, заголовки,
тела ответов, баланс или профиль. Query strings отбрасываются; все части пути вне
перечня известных служебных слов заменяются на `:value`, включая ID и возможные токены.
Неизвестные пути поэтому могут совпасть после обезличивания — это ожидаемый первый шаг.

Если `paths` пуст, список запросов мог не сохраниться или сайт использует другой путь API.
Это не означает отсутствие API. Не запрашивать полный HAR или Copy as cURL с данными
авторизации. После определения нужного endpoint подготовить отдельный сборщик схемы
JSON с разрешёнными полями и скрытыми личными значениями; секреты не должны попадать
в диагностический вывод. Ответы 401 без сессии нельзя обходить извлечением токена в чат.

## Обновления без расходования токенов

Предлагаемые стартовые интервалы: баланс — 5 минут, личный check-in — 15 минут, тарифы —
15 минут. Настраиваются по лимитам платформы, с разбросом времени и ограничением общей
параллельности. Несколько окон/сессий используют общий запрос обновления. Ошибки 429 и
Retry-After уменьшают частоту, отсутствие авторизации останавливает повторные попытки.

Все фоновые проверки — metadata GET, без вызова моделей. Для тарифного контроля перед
генерацией нужна свежесть согласно выбранному режиму защиты, а не только фоновому TTL.
Полная L3-диагностика остаётся отдельным действием по конкретной модели с указанием
количества генераций. Массовый тест не запускается при импорте списка.

## Защита от неожиданной цены

После подключения проверенных источников внедрить общий `SpendingPolicy` перед каждой
физической upstream-попыткой обоих bridges и диагностическими генерациями:

1. Верхние допустимые тарифы по входу/выходу/кэшу/инструментам, валюте и единицам оплаты.
2. Лимит роста относительно отдельно сохранённого согласованного тарифа. Автообновление
   не изменяет согласованный тариф. Рост выше порога блокирует маршрут с показом старой
   и новой цены; пользователь отдельно принимает новое значение.
3. Минимальный остаток кошелька и бюджеты сессии/дня. Счётчики бюджета хранятся отдельно
   от ограниченной истории UI, чтобы очистка старых 10 000 usage-записей не сбрасывала лимит.
4. В строгом режиме неизвестная/устаревшая цена, нераспознанная валюта, неизвестная
   группа или недоступный кошелёк блокируют платный запрос. Причина показывается до запуска.
5. Ограничение выходных токенов и оценка верхней стоимости входа с учётом tools, изображений,
   reasoning и серверных операций. При отсутствии достоверной верхней оценки нельзя
   обещать точный денежный лимит; такой тип запросов строгий режим блокирует.
6. Общий атомарный резерв бюджета между параллельными CLI-сессиями до отправки. Резерв
   сверяется по usage/платёжным данным. После обрыва с неизвестной оплатой резерв сохраняется
   как неопределённый расход до сверки, а не автоматически освобождается.
7. Каждый резервный маршрут комбо проходит ту же проверку. Цена исходной модели не
   разрешает переключение на более дорогую. Повтор после ошибки бюджета не вызывает
   генерацию и не запускает цикл перебора неразрешённых маршрутов.

Локальная проверка не может гарантировать расход до копейки, если провайдер изменяет
цену уже после проверки или списывает иначе, чем объявляет. Для абсолютного ограничения
списаний нужен также серверный лимит ключа/аккаунта у провайдера, если он поддерживается.
Это ограничение метода, а не основание показывать устаревший тариф как действующий.

## Порядок реализации и приёмка

1. **Кабинет и кошелёк.** Реестр адаптеров, отдельное хранение входа, карточка подключения,
   снимки кошелька. Проверить два аккаунта/два провайдера: без смешения кэша и учётных
   данных; истёкший вход, нулевой и неизвестный баланс, разные единицы, устаревший снимок.
2. **Check-in.** Чтение личного статуса, дата сайта, доступно/получено/выключено/неизвестно.
   Проверить смену даты и истечение авторизации. Ни одного POST получения награды.
3. **Тарифы.** Личные группы/множители, кеш/поиск, цена за запрос, история изменений и
   обогащение существующей общей витрины. Непонятная единица не конвертируется догадкой.
4. **Ограничения расходов.** Включить общий контроль во всех путях генерации и fallback.
   Проверить рост цены, конкурентные резервы, перезапуск процесса, отсутствие usage,
   обрыв после принятия запроса и превышение лимита на резервной модели: ни одного
   неразрешённого upstream-вызова.
5. **Расширение платформ.** Следующие провайдеры подключать через фикстуры обезличенных
   ответов кабинета, а не условие `if hostname` без подтверждённого контракта.

Для шагов 1–3 не нужны платные генерации. Для нового адаптера нужны публичные ссылки и
штатно подключённый аккаунт; секреты вводятся локально через интерфейс подключения.
