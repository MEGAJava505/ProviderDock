# Provider Switcher: аудит совместимости и план исправлений

Дата исходного аудита: 6 сентября 2026. Обновление: 7 сентября 2026.

Исправления после аудита описаны в [статусе реализации](stability-update-ru.md).
Новый приоритет — кошельки, check-in и витрины множества провайдеров — вынесен в
[ТЗ на кабинеты и контроль расходов](provider-portals-and-spending-ru.md).
Описанные ниже воспроизведения фиксируют исходное состояние, до этих исправлений.

Цель: дать Codex стабильный Responses API через одно ядро ProviderDock; подключать NoFX и остальные провайдеры настройками и проверенными адаптациями, сохранять историю инструментов и показывать фактическую совместимость каждой модели.

В исходном проходе выполнены чтение кода, сравнение с AgentRouter bridge, локальные проверки и подготовка плана. Затем выполнены локальные исправления приложения; проверка генерации NoFX ещё не выполнена. В рабочем дереве уже были многочисленные изменения; они сохранены.

## 1. Исходная ситуация и границы выводов

По описанию пользователя текущая схема такая:

```text
Codex, отдельный профиль OmniRouter
  → Responses endpoint OmniRouter
  → комбо: несколько моделей с приоритетами
  → NoFX и другие настроенные маршруты
```

Пользователь уже проверял, что Codex отправляет предыдущие `function_call` и `function_call_output`. Сообщены две группы симптомов: ошибки SSE/завершения/usage и повторение уже выполненных действий на следующих ходах. Исходные трассы этой проверки в рамках данного аудита не исследовались.

Это обоснованная гипотеза о проблеме промежуточного преобразования, но поведение модели само по себе не доказывает потерю истории именно в OmniRouter. Дополнительные переменные: переключение физической модели внутри комбо, смена протокола, ограничения контекста, повторная отправка запроса и поведение самой модели. Нужно сравнить одинаковый сценарий на закреплённом маршруте и через комбо.

Предоставлен адрес NoFX: `https://b45b95fa18bf.nofx.one`. Проверены два GET без учётных данных:

| Запрос | Результат | Что установлено |
| --- | --- | --- |
| `/` | HTTP 200, HTML, заголовок `nofx - AI API Gateway` | Сайт доступен из среды проверки |
| `/v1/models` | HTTP 401, JSON с полями `code`, `message` | По этому пути требуется авторизация; каталог не получен |

Ответ 401 ещё не доказывает правильность API-префикса: его мог вернуть общий слой авторизации. `/v1` — кандидат для настройки, который требуется подтвердить авторизованным discovery. Точный ID модели, возможности Responses/Chat и состав комбо пока не установлены. Обозначение Sol из разговора не подменяется предположительным ID.

## 3. Подтверждённые проблемы текущего ProviderDock

Следующие четыре случая воспроизведены отдельным локальным Node.js сценарием на собранных модулях. HTTP-ответы и поток созданы в памяти, `fetch` подменён; запросов к моделям не было.

### P0-1. Native Responses не нормализует `total_tokens`

Место: `src/bridge/responses/responses-stream-state.ts`, метод `observe`, и native JSON-путь в `responses-bridge-server.ts`.

Входной `response.completed` с `usage: {input_tokens: 10, output_tokens: 2}` пересылается без `total_tokens`. Chat-переводчик уже имеет отдельную нормализацию usage, но она не применяется к native Responses.

Нужен общий нормализатор завершённого ответа и usage для JSON и SSE. Если оба счётчика достоверны, отсутствующий total можно вывести как 12. Отсутствующие счётчики нельзя выдавать за измеренные нули; неизвестные данные должны оставаться неизвестными в отчёте расходов. Формат на проводе проверить на целевой версии Codex.

### P0-2. Сетевой обрыв может превратиться в успешное завершение

Место: `src/bridge/responses/responses-stream-relay.ts`, обработка исключения и `forceFailure`; `responses-stream-state.ts`, метод `buildTerminalRepair`.

Воспроизведение: поток выдаёт один `response.output_item.done`, затем чтение завершается исключением до terminal event. Relay передаёт `forceFailure` только для ошибок декодирования/протокола. Обычная транспортная ошибка не учитывается, и состояние генерирует `response.completed` при отсутствии известных pending items.

Завершение одного наблюдавшегося item не доказывает завершение всего response: последующие items могли не дойти. Это риск ложного успеха и неверного состояния сессии.

### P0-3. Doctor считает `response.failed` успешным streaming-тестом

Место: `src/diagnostics/provider-doctor.ts`, `checkStreaming` и `isTerminalStreamEvent`.

Сейчас `response.completed`, `response.failed` и `response.incomplete` объединяются в один признак `terminalSeen`. При отсутствии дублей получается `PASS` даже для явно неуспешного ответа. Воспроизведён именно `response.failed` → `PASS`.

Нужно различать доставку terminal event, успешность генерации и валидность завершённого ответа. Ошибка провайдера не обязательно означает неподдерживаемый протокол, но успешным результатом пробы она быть не должна.

### P0-4. Doctor не доказывает использование tool result

Место: `src/diagnostics/provider-doctor.ts`, `checkTools`, проверка `finalText`.

После синтетического tool result любой непустой текст даёт `PASS`. Воспроизведён второй ответ с посторонним текстом и повторным вызовом того же инструмента под новым `call_id`: Doctor всё равно вернул `PASS`.

Кроме того, continuation строится из одного извлечённого вызова, а не из полного `output` первого ответа. Для reasoning-моделей это может само по себе делать пробу нерепрезентативной: официальный сценарий требует возвращать соответствующие reasoning items вместе с результатами инструментов. [OpenAI: Function calling](https://developers.openai.com/api/docs/guides/function-calling).

### Дополнительные пробелы, установленные чтением кода

- `apiType: auto` в `ResponsesBridgeServer.fetchRoute` фактически выбирает Responses. Результат Doctor, нашедшего рабочий Chat, сам по себе не задаёт протокол следующего рабочего запроса.
- Обычный запуск generic Responses с bearer-авторизацией может обойти managed bridge: `CodexLauncher.resolveRoute` включает его только при определённых условиях. Prompt-profile launch, напротив, явно устанавливает `forceManagedBridge`. Пользовательский выбор маршрута должен давать предсказуемую защиту независимо от формы запуска.
- API-протокол задаётся на уровне провайдера. Для разных моделей одного URL может требоваться разный протокол; текущей пары `providerId + modelId` в логическом маршруте недостаточно для хранения всех вариантов совместимости.
- Discovery помечает найденные модели `ONLINE` в `model-catalog.ts`. Наличие в списке не подтверждает успешную генерацию, tools или поток. В UI эти признаки нужно разделить.
- UI предлагает главным образом «Тест L1». Более глубокие уровни есть в backend/CLI, но не представлены как понятный тест агентской совместимости.
- Совместимость клиента в `doctor-capability-snapshot.ts` выводится из типа протокола; это не равнозначно сквозной проверке реального Codex через bridge.
- Существующий turn ledger полезен для одинаковых запросов и повторного использования разрешённого `call_id`. Семантически одинаковая команда с новым ID — другой случай; безусловная блокировка одинаковых аргументов сломает законные повторные чтения, проверки и polling.

## 4. Что взять из AgentRouter bridge

Изучен публичный репозиторий [agentrouter_for_codex](https://github.com/MEGAJava505/agentrouter_for_codex), состояние `0f0e1a160c027a1f6a73ef120cd3048ae9c7c354`.

Полезные элементы для выборочного переноса:

- [Request translator](https://github.com/MEGAJava505/agentrouter_for_codex/blob/0f0e1a160c027a1f6a73ef120cd3048ae9c7c354/src/request-translator.mjs): сборка assistant/tool history, сопоставление имён инструментов, обработка дополнительных разновидностей tools.
- [Response translator](https://github.com/MEGAJava505/agentrouter_for_codex/blob/0f0e1a160c027a1f6a73ef120cd3048ae9c7c354/src/response-translator.mjs): сборка streamed tools и нормализация Chat usage.
- [Server](https://github.com/MEGAJava505/agentrouter_for_codex/blob/0f0e1a160c027a1f6a73ef120cd3048ae9c7c354/src/server.mjs): per-model native circuit и выбор Chat после некоторых native-сбоев, heartbeat, восстановление отдельных событий.
- [Live smoke](https://github.com/MEGAJava505/agentrouter_for_codex/blob/0f0e1a160c027a1f6a73ef120cd3048ae9c7c354/scripts/live-smoke.mjs): второй streaming-ход проверяет отсутствие повторных function calls. Его стоит усилить проверкой содержимого результата.

Этот bridge также не следует считать универсально корректным образцом: native relay использует похожее условие синтетического успеха после закрытия потока; Chat request translator пропускает reasoning items. Перенос каждой адаптации должен сопровождаться проверкой её ограничений. Identity headers AgentRouter остаются только в его профиле.

## 5. Предлагаемая архитектура

```text
Codex
  → стабильный локальный Responses endpoint ProviderDock
  → проверка истории + учёт состояния запроса
  → выбор проверенного маршрута для provider/model
  → native Responses ИЛИ Responses↔Chat адаптер
  → scoped-правила провайдера
  → API NoFX / AgentRouter / GoRouter / другого провайдера
```

Один набор исправлений транспорта, сериализации истории и учёта состояния используется всеми провайдерами. Отдельные настройки определяют авторизацию, URL, имена полей, реально поддерживаемые параметры и проверенный протокол модели. Произвольное превращение всех провайдеров в полностью эквивалентный Responses API обещать нельзя: при отсутствии нужной возможности bridge должен показывать конкретное ограничение.

Результат диагностики хранить для сочетания:

```text
provider ID + fingerprint подключения + точный model ID
  + upstream protocol + версия адаптации + версия набора проб
```

Fingerprint включает origin/base path и существенные настройки маршрута, но не значение ключа. Смена ключа или подключения инвалидирует старые выводы о доступе. Отдельно сохраняются дата проверки, проверенные capabilities, ограничения и способ получения usage. Одинаковые model IDs у разных провайдеров автоматически не объединяются в доказанно эквивалентные модели.

Правила совместимости должны быть версионированы и ограничены конкретным профилем/маршрутом, с миграцией существующих профилей. Сначала добавить только правила, подтверждённые NoFX и текущими локальными воспроизведениями; полноценный новый plugin framework для этого не нужен.

### Транспорт и завершение

- Общая проверка terminal response, `output`, статусов items, согласованности tool IDs и usage.
- `total_tokens = input_tokens + output_tokens` только для валидных счётчиков одного ответа; не прибавлять reasoning/cache повторно, не суммировать накопительные снимки usage как отдельные запросы. Официальная структура содержит основные счётчики и их детализацию. [OpenAI: Response reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create).
- Ошибки сети, timeout и cancel до доказанного завершения сохраняют неуспех. Сам по себе EOF, `[DONE]` или отсутствие pending items недостаточны для генерации успешного Responses completion.
- Для Chat требуется корректный `finish_reason` и полностью собранные items; `length` не превращается в обычное успешное завершение. Для native Responses основной источник истины — валидный terminal response.
- Восстановление отсутствующего terminal допускается только при отдельно установленном надёжном сигнале завершения и проверенных данных, по ограниченному правилу конкретного маршрута.
- Не более одного terminal event; после него закрыть downstream и освободить upstream без ожидания ещё одного маркера. Heartbeat поддерживает соединение, но не доказывает прогресс модели.
- Каждое синтетическое событие проходит те же проверки, ledger и телеметрию, что и обычное.

### История инструментов

- Сохранять порядок и связь `function_call.call_id` ↔ `function_call_output.call_id`; при Chat-переводе это `assistant.tool_calls[].id` ↔ `role: tool, tool_call_id`.
- Не заменять результаты служебным текстом вроде «инструмент уже выполнен», не выбрасывать результаты и не обрезать только половину пары.
- Поддержать параллельные вызовы, результаты в другом порядке, несколько последовательных шагов и custom tools, используемые целевой версией Codex.
- В native-пути сохранять reasoning items. Зашифрованное состояние нельзя произвольно переносить между независимыми провайдерами или считать сохранённым после записи в нестандартное Chat-поле.
- Chat fallback разрешать только для представимых возможностей конкретного запроса. Неизвестные tool types, вложения или stateful-ссылки должны давать объяснимый отказ, если эквивалентного преобразования нет.
- Существующий stateless Chat-путь явно отвергает `previous_response_id`/`conversation`; сохранить это до появления полноценного хранилища ответов. Такое хранилище не требуется для первого этапа, если Codex действительно присылает полную историю.
- Отделить повтор transport request от нового решения модели повторить действие. Ledger не даёт общей гарантии exactly-once для внешних инструментов, которые исполняет Codex; для сомнительного повтора нужен диагностируемый останов, а не выдуманный результат.

### Комбо и резервные маршруты

Выбранные provider/model/protocol закрепляются за сессией. После сбоя маршрут не должен незаметно возвращаться на приоритетный provider на каждом следующем ходе.

Fallback внутри текущего запроса допустим только при доказанном отказе до вывода/выдачи инструмента и известном состоянии выполнения. Отсутствие видимого текста само по себе недостаточно. После частичного ответа, tool call или неоднозначного обрыва автоматический повтор запрещён.

Переключение на границе следующего завершённого шага требует разрешённой истории tools и возможности представить весь необходимый контекст целевым протоколом. Несовместимое reasoning/provider-state означает останов с понятным объяснением, а не молчаливое удаление состояния.

Если upstream остаётся комбо OmniRouter, ProviderDock может видеть только внешнюю оболочку. Без достоверных route metadata он не знает, какая физическая модель выбрана, и не может гарантировать сохранность преобразования внутри OmniRouter. Это ограничение показывать в интерфейсе. Для диагностики NoFX нужен прямой маршрут с закреплённой моделью.

## 6. Проверка NoFX с небольшим расходом

Сначала все структурные дефекты исправляются и проверяются локально. Затем один выбранный model ID проверяется с ключом из локального secret store. Рабочие prompts, файлы проекта и настоящие изменяющие инструменты для этой пробы не нужны.

| Уровень | Проверка | Расход |
| --- | --- | --- |
| Каталог | GET моделей и сохранение metadata | Без генерации; не обещать отсутствие платы со стороны любого провайдера |
| Минимальный ответ | Короткий ответ одной выбранной модели | 1 inference request |
| Поток | Успешный валидный terminal, usage и output | 1 inference request |
| История | Вызов синтетического инструмента и следующий ход | 2 inference requests |
| Расширенная история | Несколько ходов, параллельные/custom tools | Отдельный запуск с заранее показанным числом запросов |

Минимальный полный набор для одного протокола — до четырёх inference-запросов после discovery. Проверка второго протокола — отдельный набор, а не скрытая бесконечная серия повторов. В первый диагностический запуск входит только выбранная модель; не весь каталог и не все провайдеры.

Сценарий проверки истории:

1. Задать цель: вызвать диагностический инструмент один раз, затем вернуть полученный от него код.
2. На первом ходе проверить ровно один ожидаемый вызов и корректные аргументы.
3. После ответа модели создать случайный код, например `receipt-<random>`. Он должен появиться только в результате инструмента, а не в исходном prompt или аргументах.
4. Передать на второй ход исходную историю, полный совместимый `output` первого ответа и tool result с тем же `call_id`. Tools оставить доступными, выбор — `auto`; принудительный `none` скрыл бы дефект повторов.
5. Убедиться, что второй ответ вернул правильный код, не вызвал инструмент снова и корректно завершился. Повторный вызов в этой пробе не исполнять.

Один успешный прогон подтверждает этот сценарий в данный момент, а не вечную безошибочность модели. Для расширенной проверки применять новые случайные коды и хранить число успешных/неуспешных прогонов.

Сравнение путей выполнять последовательно: прямой NoFX по доступному протоколу → тот же провайдер через managed ProviderDock → при необходимости закреплённый маршрут OmniRouter → комбо. Расширять сравнение только когда предыдущий результат оставляет вопрос о месте сбоя.

Перед запуском показывать модель, протокол, число запросов и лимит выходных токенов каждого запроса. Учитывать reasoning в поддерживаемом лимите. При слишком маленьком лимите и `incomplete` результат обозначать как неустановленный для истории, а не как доказанное отсутствие tools. Денежную оценку показывать только при известных тарифах и с обозначением её приблизительности; расходы Doctor тоже включить в учёт.

## 7. Изменения интерфейса

Основной поток пользователя: «Добавить провайдера» → URL + ключ → «Импортировать модели» → выбрать одну модель → «Проверить для Codex» → результат → запуск.

Разбор URL/cURL и импорт уже есть. Улучшения:

- Показать результат фонового discovery после сохранения; ошибки не терять в пустом `catch`. Объяснять различие сайта и API base URL, предлагать проверенные кандидаты префикса без пересылки ключа на другой origin.
- Сохранять полученный каталог и время обновления; не удалять ручные модели при сбое discovery. Поддержать pagination через адаптер, если конкретный API её использует.
- Разделить состояния «найдена в каталоге», «отвечает», «поток проверен», «история инструментов проверена» и «проверено через ProviderDock». Зелёный статус по одному GET моделей исключить.
- В общей таблице моделей показывать provider, точный model ID, проверенный протокол, дату, уровень теста и ограничения. Для каждой строки — отдельная проверка выбранной модели; массовый запуск должен явно показывать расход.
- Для текущего запуска показывать реальный известный маршрут и причину переключения. Внешнее комбо без раскрытого маршрута обозначать как неизвестный внутренний маршрут.
- В отчёте ошибки показывать этап: подключение, генерация, поток, история, fallback; ожидаемое/полученное событие и применённое исправление. Например: «Провайдер прислал ошибку вместо завершённого ответа», «История передана, но тестовая модель повторила вызов».
- Экспорт диагностики: версии, обезличенные correlation IDs, типы/порядок событий, количество пар tool call/result, HMAC-отпечатки содержимого в пределах пробы, terminal и источники usage. Без ключей, raw reasoning и содержимого пользовательских prompts. Полные тела допустимы для синтетических локальных fixtures.

## 8. Порядок реализации и критерии приёмки

| Этап | Работа | Критерий готовности |
| --- | --- | --- |
| 1. Общие дефекты | Регрессионные тесты четырёх воспроизведений; нормализатор usage/terminal; различение сетевого обрыва и успеха; строгий Doctor | Все четыре прежних дефекта закрыты, существующие проверки проходят |
| 2. NoFX, одна модель | Подтвердить API-префикс и каталог; выбрать точный model ID; проверить прямой маршрут и managed bridge; добавить только необходимые правила | Через ProviderDock проходят поток и тест случайного tool receipt; точный протокол и ограничения записаны |
| 3. Выбор протокола | Перенести результат диагностики в выбор маршрута provider/model; предсказуемый managed bridge при запуске; миграция профилей | `auto` выбирает проверенный режим конкретной модели, не угадывает по бренду |
| 4. Комбо | Проверить закрепление маршрута, разрешённую историю и барьеры повторов; показывать причины switches | При обрыве после tool call нет повторного upstream-запроса; при безопасном отказе выбран совместимый резерв |
| 5. UI и прочие провайдеры | Понятные импорт/пробы/стоимость; затем GoRouter, Just Do Work, Tabi AI, Sick AI, KK Token.cc | Каждый маршрут имеет независимый отчёт; неизвестная совместимость не помечается успешной |

Названия последних провайдеров сохранены как в запросе. Их адреса, auth и возможности не угадываются. Для подключения каждого потребуется точный base URL; ключ вводится локально. Если достаточно generic adapter и профиля, отдельный код провайдера не добавляется.

Минимальная регрессия перед реальными пробами: отсутствующий total при известных счётчиках; неизвестный usage; пустой/отсутствующий terminal output; дубли и конфликты SSE; обрыв в аргументах инструмента и между items; failed/incomplete terminal; несколько tool pairs и обратный порядок параллельных результатов; custom tool mapping; повтор с тем же ID и новый ID в синтетической пробе; fallback после отказа и запрет после выдачи инструмента; одинаковые IDs у разных провайдеров; смена протокола модели и устаревшая диагностика.
